DMA Kernel Mechanics
--------------------

When packets are arriving from the network :

Normal path:
  NIC (network card) --DMA--> kernel space (network socket buffers sk_buff) --> copy --> user space buffer

Kernel bypass (DPDK / OpenOnload):
  NIC (network card) --DMA--> user space buffer directly (all network stack is moved into user space)

When the network stack moves to user space, the NIC can be given the physical address of your user space buffer directly,
so it writes the packet there without any CPU involvement in the transfer.
The copy disappears. The latency drops. The CPU stays free (can be done with SolarFlare OpenOnLoad / DPDK).

Without kernel bypass, the NIC still does DMA but into kernel buffers.
You still have to copy from there into user space, which is the hop you are eliminating.

ByteBuffer.allocateDirect (in Java) reduces copies within the JVM I/O path but you are still going through the kernel.
Completely different level of the stack (allocation off heap in a fixed location vs dynamic in heap because of GC).

Kernel bypass alone:
  NIC → user space buffer (off-heap) → copy to JVM heap → app reads

Kernel bypass + allocateDirect:
  NIC → user space buffer (off-heap) → app reads directly
                                        (no heap copy)

Without allocateDirect, your app still needs to copy the data from the off-heap NIC buffer into a heap byte[] for the JVM to work with it normally.
That is an extra copy you want to eliminate.
So doing both is the right instinct — kernel bypass removes the kernel copy, allocateDirect removes the heap copy.

So in practice:
- If using OpenOnload — it works transparently at the socket level, so allocateDirect + socket reads gets you most of the benefit cleanly from Java
- If using DPDK via JNI — you manage native buffers yourself, ByteBuffer.wrap() over native memory, and never touch the heap at all
